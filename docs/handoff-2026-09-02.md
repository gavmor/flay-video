## What was done this session

### 1. Smoke test (`docs/spike/nvdec_cvcuda_smoke_test.py`)

Original script measured ~400 fps for decode+cvtcolor+resize on
1080p — but had no VRAM pre-flight and no failure marker, so
mid-run OOMs on a memory-constrained host produced a misleading
traceback without any "INCOMPLETE" signal.

**Fix applied** (modified file, +106/-57):

- Pre-flight VRAM floor check (`torch.cuda.mem_get_info()` + 2 GB
  hard floor, clean early abort with `FATAL` message).
- `current_step` tracker + `try/except BaseException` wrapper around
  the work blocks, so any failure prints
  `INCOMPLETE — failed during {step}` before re-raising the
  traceback.
- `N_FRAMES` and `VIDEO_PATH` constants moved above the VRAM check
  (an `NameError` I caught in the first verification pass — the
  error message referenced `N_FRAMES` before it was defined).

**Verified end-to-end:** N=100 on a memory-constrained local 3090
ran to completion (436.9 fps full pipeline, matching the original
~400 fps measurement); N=500 with mid-run OOM printed the
`INCOMPLETE — failed during step 4 (decode+cvtcolor+resize)` marker
as designed; low-VRAM path printed the `FATAL` early-abort message
without a mid-run OOM.

**What this is NOT:** dynamic N scaling, portable benchmarks, or
host-independent measurement. The user explicitly asked for simple
and reliable, not flexible. N_FRAMES stays at 500 for apples-to-
apples comparison with the original ~400 fps measurement.

## Context the next agent should know

- **The user's preference pattern in this session** was "simple
  and reliable, not flexible." Three times in this session I
  offered the more-impressive-but-bigger option (dynamic N
  scaling, fork-and-PR-the-repro, full orchestrator script) and
  the user picked the smaller, more honest option each time
  (capped max-frames, gist/empty-repo-only-no-PR, leave the
  decision for later). When offering paths, lead with the small
  one.
- **The user's voice** in upstream reports: straightforward,
  technically precise, references prior issues by number, doesn't
  overpromise. Issue #298's body is a good template for future
  upstream reports.
- **The exhaustive job is honest about its bound.** Don't try to
  make it look more capable than it is. `--max-frames` is a real
  safety valve for a real bug, not a tuning knob.
- **The smoke test fix is intentional minimalism.** Resist the
  urge to add dynamic N scaling or host-portable logic — the
  script's purpose is to reproduce the original ~400 fps
  measurement, and changing N or the test environment defeats
  that.
- **The bug is in the cvcuda release path, not PyNvVideoCodec.**
  Filing the upstream report against CV-CUDA (not PyNvVideoCodec)
  is correct. PyNvVideoCodec has no public issue tracker (source
  on NVIDIA NGC), but the crash signature is from cvcuda's object
  chain, so the CV-CUDA report is the right one regardless.
